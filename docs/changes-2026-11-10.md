# Changes 2026-11-10: rebuild into six modules

Branch `rebuild-2026-11`, cut from `uptake-2026-11-06`. Not merged, not deployed.

RINDA is still **deployable for controlled evaluation, not validated for intervention decisions**. This release
extends the existing application. No earlier screen or endpoint was removed.

## Rules now enforced on the server

- **A forecast only sends an aircraft to look.** Every forecast-planned target is inspect-only. Before this release a
  forecast "formation" site was planned as verify-and-treat.
- **Treatment missions** can include only habitats with a supervisor-authorised drone intervention. Approval re-checks this.
- **Authorising treatment** needs a verified observation with larvae found, a habitat suitability assessment, a protocol
  reference and a supervisor. Water seen without a larval sample no longer qualifies. This setting, and every other
  protocol threshold, lives in `config/protocol_settings.json` and is marked awaiting approval. No threshold is invented.
- **Refusals are records.** A supervisor's decision not to treat is stored with its reason.
- **Returning or rejecting an observation, and rejecting a mission, need a reason.**
- **A follow-up must include dipping.** "Not sampled" cannot close an intervention.
- **Missing is never zero.** Counts and indicators with no records return null and read "No data available".
- **Field locations and officer names** need a field, analyst or supervisor role. Public and programme-manager views get
  counts by cell.
- **The 5 November 2026 audit** (`config/model_audit.json`) travels with every forecast response and is shown on every
  forecast screen. No target A model can be approved while `label_reconstruction_complete` is false.
- **Synthetic stays synthetic.** Demonstration accounts can only load SYNTHETIC datasets and records; a model trained on
  them is a `synthetic_fixture` and can never be approved.

## Data and models

- **Historical datasets** (`/datasets`): CSV, Parquet or GeoJSON points for eleven kinds of data. Each upload gets an
  eleven-check quality report. A person confirms it before use. The original file is kept; confirming writes a new
  versioned Parquet file. The same file cannot be registered twice.
- **Training** (`/training/runs`): runs as a separate process. Temporal split with an embargo of horizon + 2 days,
  calibration on its own window, one scoring of the test window, held-out 500 m blocks, baselines, reliability,
  feature importance, fixed seed and a prediction hash. A run ends as a candidate and changes nothing RINDA displays.
- **Targets A to E** are separate. Only A has labels today. A table for one target cannot train another.
- **Check run on 10 November:** the archived 7-day table gave PR-AUC 0.630 against 0.615 for the 30-day water-frequency
  rule. This is the Paper 1 label set, which the audit covers; it is a pipeline check, not a result.
- **Connectors** (`server/connectors.py`): Earth observation, IoT, meteorology, entomology, drone. Each reports
  "not connected" and fetches nothing until credentials exist. Pushed records are validated, normalised, de-duplicated
  and logged. Telemetry from commissioned nodes is now stored as readings with units and range flags.
- **Geography:** sector boundary from geoBoundaries (NISR 2012, CC BY 4.0) and an interpreted, preliminary marshland
  outline. **Cell boundaries are not bundled:** the outlines to hand were GADM's, whose licence forbids redistribution
  in a public repository. The cell filter and cell names stay empty until NISR cell files are added to `config/geo`. 301 of the 600 monitoring locations fall inside the sector.
- **Satellite metadata:** 2,061 Sentinel-1 RTC and Sentinel-2 L2A scenes from the repository catalogues. Rasters are
  not stored in RINDA.

## Database

Migration 6, additive. New tables: `data_sources`, `ingestion_runs`, `dataset_versions`, `environmental_observations`,
`entomological_samples`, `raster_products`, `administrative_areas`, `training_runs`, `model_registry`,
`observation_photos`. New columns: `observations.sampling_method`, `observations.anopheles_larvae_count`,
`interventions.habitat_suitability`, `.protocol_status`, `.decision_reason`, `missions.kind`, `.flight_result`,
`.decision_note`. Existing rows are untouched; existing missions read as inspection flights.

PostgreSQL with PostGIS was not introduced. SQLite holds 600 points and five polygons comfortably. A national
deployment with many districts and concurrent writers would need it; the queries are confined to `geo.py` and
`surveillance.py`.

- Phone (375 px) and tablet (768 px): no sideways scrolling on the seven main screens; buttons at least 38 px high.

  three times over. Linux peak RSS is measured by CI, which now also calls the new endpoints.

## Not done, or not checked

- **Docker build and serve check:** Docker is not installed on the development machine. CI runs it on push.
- **Clicked through in a browser:** screens were loaded and inspected, but the full journey (assign, record, review,
  authorise, mission, result, follow-up) was exercised through the API tests, not by hand in the interface.
- **Kinyarwanda:** only the six module names were added, as a draft. Field screens keep the earlier draft. A reviewed
  translation needs RBC and district teams.
- **Photographs are not kept offline.** An observation saved offline is queued; its photographs are not, and the
  officer is told so.
- **Live connections:** connector classes exist; none fetches. Raster processing needs a worker outside the web process.
- **Costs:** cost per inspected or treated habitat needs programme cost records.
- **Resistance surveillance:** shown only if a loaded entomology file carries it.
- **Basemap:** street tiles now come from OpenStreetMap, because the CARTO tiles show an "API key required" mark. A
  programme deployment should use its own tile server.
- **`config/operational_rules.json`** still words the high-priority rule the old way (noted on 16 October).
